# Ход-отчёт: анализ заполнения ufiles и retention backup

Дата: 2026-08-06

## Цель

Определить причину заполнения `/mnt/ufiles`, сохранить две последние полные
резервные копии и предотвратить повторное заполнение диска.

## Что сделано

- Проверены filesystem, занятые блоки и inode `/mnt/ufiles`.
- Найдено 42 полных поколения в `/mnt/ufiles/backups` за период с 2026-06-26
  по 2026-08-06.
- Подтверждено отсутствие retention в `osnova-backup.sh.j2`.
- Подготовлен retention на два последних успешно завершённых поколения.
- Новая копия сначала создаётся как скрытый staging-каталог и публикуется
  атомарным переименованием только после успешного завершения.
- При ошибке незавершённый staging-каталог удаляется обработчиком `EXIT`.
- Подготовлен dry-run удаления 40 старых поколений с сохранением копий за
  2026-08-05 и 2026-08-06.

## Изменённые файлы

- `ansible/group_vars/all.yml`
- `ansible/templates/osnova-backup.sh.j2`
- `scripts/backup/prune-osnova-backups.sh`
- `docs/reports/2026-08-06-ufiles-backup-retention.md`

```text
ansible localhost -c local -m ansible.builtin.template ...
bash -n /tmp/osnova-backup.rendered
git diff --check
```

## Проверки

- `/dev/sdf1`: 916 GiB, занято 871 GiB до очистки.
- Inode: занято около 10%, исчерпание inode исключено.
- Одно последнее поколение занимает не менее 19.2 GB; часть root-only файлов
  не вошла в непривилегированный подсчёт.
- Jinja-шаблон успешно отрендерен.
- Отрендеренный shell-скрипт прошёл `bash -n`.
- Изолированный тест retention сохранил две новые копии, выбрал старые и
  проигнорировал `.incomplete` каталог.

## Результат

Первопричина установлена: ежедневный скрипт создавал независимую полную копию
без удаления старых поколений. Декларативное исправление подготовлено.

Очистка runtime не выполнена: `sudo` потребовал интерактивную аутентификацию,
поэтому команда завершилась до запуска `rm`. Ни один backup-каталог не удалён.

## Найденные проблемы

- 42 полных backup-поколения занимают основную часть диска.
- В установленном скрипте отсутствует retention.
- Применение Ansible и удаление root-owned файлов требуют локальной
  sudo-аутентификации.

## Риски

- Удаление старых копий необратимо.
- Хранение только двух дневных копий даёт короткое окно обнаружения логической
  порчи или незаметного удаления данных.
- Полные ежедневные копии не заменяют внешнюю/off-site резервную копию.

## Что осталось

1. Удалить подтверждённые 40 старых поколений с sudo.
2. Проверить, что остались два каталога и корректный `latest`.
3. Проверить освобождённое место через `df`.
4. Выполнить Ansible `--check --diff`, затем применить backup-шаблон.
5. Проверить следующий запуск timer и журнал `/var/log/osnova-backup.log`.

## Следующий шаг

Сначала повторить dry-run, затем выполнить подтверждённую очистку из локального
root-сеанса:

```bash
./scripts/backup/prune-osnova-backups.sh --dry-run
sudo ./scripts/backup/prune-osnova-backups.sh --apply
```

После очистки активировать декларативный retention.

## Rollback

- Изменения шаблона откатываются удалением `backup_retention_count` и блока
  staging/retention из `osnova-backup.sh.j2`.
- Удалённые backup-поколения восстановить без другой копии невозможно.
